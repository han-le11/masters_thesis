%% WHAT is PDF/A
%%
%% PDF/A is the ISO-standardized version of the pdf. The standard's goal is to
%% ensure that he file is reproducable even after a long time. PDF/A differs
%% from pdf in that it allows only those pdf features that support long-term
%% archiving of a file. For example, PDF/A requires that all used fonts are
%% embedded in the file, whereas a normal pdf can contain only a link to the
%% fonts in the system of the reader of the file. PDF/A also requires, among
%% other things, data on colour definition and the encryption used.
%% Currently three PDF/A standards exist:
%% PDF/A-1: based on PDF 1.4, standard ISO19005-1, published in 2005.
%%          Includes all the requirements essential for long-term archiving.
%% PDF/A-2: based on PDF 1.7, standard ISO19005-2, published in 2011.
%%          In addition to the above, it supports embedding of OpenType fonts,
%%          transparency in the colour definition and digital signatures.
%% PDF/A-3: based on PDF 1.7, standard ISO19005-3, published in 2012.
%%          Differs from the above only in that it allows embedding of files in
%%          any format (e.g., xml, csv, cad, spreadsheet or wordprocessing
%%          formats) into the pdf file.
%% PDF/A-4: based on PDF 2.0, standard ISO19005-4, published in November 2020.
%%
%% PDF/A-1 files are not necessarily PDF/A-2 -compatible and PDF/A-2 are not
%% necessarily PDF/A-1 -compatible.
%% Standards PDF/A-1, PDF/A-2 and PDF/A-3 have two levels:
%% b: (basic) requires that the visual appearance of the document is reliably
%%    reproduceable.
%% a (accessible) in addition to the b-level requirements, specifies how
%%   accessible the pdf file is to assistive software, say, for the physically
%%   impaired.
%% The PDF/A-4 standard does not have additional levels like in the earlier
%% standards.
%% For more details on PDF/A, see, e.g., 
%% https://www.loc.gov/preservation/digital/formats/fdd/fdd000318.shtml or
%% https://www.pdfa.org/resource/iso-19005-pdfa/
%%
%%
%% WHICH PDF/A standard should my thesis conform to?
%%
%% Either to the PDF/A-2b or the PDF/A-1b standard. If all the figures and
%% graphs used in thesis work do not require transparency features, use either
%% PDF/A-1b or PFDF/A-2b. If you have figures with transparency
%% characteristics, use the PDF/A-2b standard. However, drawing applications
%% often use the transparency parameter, setting it to zero, to specify opacity
%% and get the basic 2-D visualisation. As a result, validation of PDF/A-1b
%% will fail. Use PDF/A-2b if PDF/A-1b validation fails.
%% Do not use the PDF/A-3b standard for your thesis.

%% changed. In addition to not adhering to Aalto's visual guidelines, you may
%% have difficulties in producing a PDF/A-compliant PDF.
%%
%%

%%

The limitation of large language models (LLMs) is that their knowledge is restricted to their training data and context window.
If a user asks an LLM about information that is not in the model's knowledge, such as a Google calendar event or a file, the LLM cannot answer or just makes things up. 
This restriction of LLMs has brought about a new paradigm of agentic software systems, shifting AI's capabilities from passive text generation to active tool use.
AI applications, powered by LLMs in their core, are connected to external tools — be they databases, web contents, or local files — to bring external data to the context window of LLMs. 
Modern autonomous software systems utilize LLMs and other machine learning algorithms to perceive the user's prompt, decide on the best approach, take actions by using tools and information available to them, and learn from user feedback.
However, as the number of AI applications and external tools increases, the integration problem grows quadratically, as known as the \textit{N$\times$M} integration problem \cite{ray2025survey}. 
Without a shared interface, every \textit{M} number of AI applications requires a bespoke integration for every \textit{N} external tool that it integrates. 
Therefore, AI applications need a robust framework to solve the explosion of \textit{N$\times$M} integrations and to standardize the communication of LLMs with external resources.

As a result, the Model Context Protocol (MCP), introduced by Anthropic in November 2024, has emerged as a middleware layer that standardizes how AI agents connect to external systems and interact with the world beyond the training data of their LLMs \cite{anthropic_mcp_intro}.
MCP defines a unified communication layer, based on the JSON-RPC 2.0 protocol \cite{jsonrpc2020}, through which LLMs can discover, invoke, and interact with external tools and resources, such as databases, files, and APIs.
From the point of view of scalability, MCP aims to solve the bottleneck of the \textit{N$\times$M} integration problem \cite{ray2025survey}.
In MCP architecture, the LLM's reasoning is separated from tool execution, so that new tools can be added to the MCP-based production system without modifying the underlying agentic pipeline. 
As a result, within months of its release, MCP is rapidly adopted by industry vendors, including Google, GitHub, and Figma.
Google's MCP server ecosystem spans multiple first-party remote servers hosted on Google infrastructure, covering both Google Cloud products and consumer- or developer-facing Google services, including a dedicated set of Google Workspace MCP servers for Drive, Gmail, and Calendar \cite{google_mcp2026}.
For example, Google Calendar MCP server allows AI agents to access a consented user's Google Calendar data and acts as an AI assistant to check availability or create and update events \cite{google_calendar_mcp}.
The GitHub MCP server allows AI assistants to perform common GitHub operations as a developer, such as reading code repositories, managing issues and pull requests, and retrieving file contents \cite{github-mcp-server}.
Figma MCP server bridges the gap between design and production by feeding layout data directly to AI coding tools. 
By June 2026, the MCP ecosystem is estimated to have grown to over 17,000 MCP servers, ranging from community-developed to enterprise-grade MCP servers \cite{glama_mcp_servers_2026}.

\section{Background of MCP}
\label{chap:mcp_background}
% ============================================================
% what this chapter is about
This chapter studies the background, core architectural components, and workflow of Model Context Protocol (MCP). 
In addition, current landscape of the MCP ecosystem is analyzed by studying MCP adoption and use cases relevant to the field of higher education.

\subsection{Overview of Model Context Protocol}
% Explain what MCP is and Why it was introduced
Introduced by Anthropic in November 2024, MCP is an open-source standard that defines how an AI application exchanges context with external tools and data sources through a uniform interface, rather than through customized, tool-specific integration processes \cite{anthropic_mcp_intro}.
Hence, MCP can reduce custom code for every AI-to-tool connection and solve the \textit{N$\times$M} integration problem introduced in Chapter \ref{chap:intro}. 
This scalability challenge occurs when there are \textit{M} number of AI clients (e.g., AI-based chat applications, model APIs, agent frameworks, AI coding assistants) that need customized integration to \textit{N} external tools and resources (e.g., service platforms, APIs, databases, internal services, or files) \cite{ray2025survey}. 
For instance, if there are 4 different AI applications and 3 different tools, e.g., 3 APIs, then developers need to build 12 separate integrations.

Figure~\ref{fig:mcp_simple} illustrates MCP on a conceptual level. 
On one side sit AI applications that a user interacts with — chat interfaces such as Claude Desktop, AI coding assistants such as Claude Code. 
On the other side sit the data sources and tools an organization already operates, such as databases, file systems, development tools, and productivity tools. 
Without a shared protocol, connecting every AI application to every tool requires a custom integration for each pair, because every tool can have its own authentication, schema, and error handling.
MCP is positioned in between as a single standardized protocol: each AI application implements MCP once to reach any MCP-compliant tool or data source, and each tool or data source implements MCP once to be reachable by any MCP-compliant application, reducing the \textit{N$\times$M} integration problem into a simpler \textit{N$+$M}.
The interactions between AI applications and resources and tools are bidirectional because MCP is not just limited to the AI application merely reading from a resource. 
A tool can, for example, act on a request initiated by the model, and a data source can push updated context back to the application without a new request being issued each time.

MCP follows a host-client-server architecture illustrated in Fig. \ref{fig:mcp_architecture} \cite{mcp_architecture}. 
A host is an AI application, such as Claude Desktop, that embeds one or more MCP clients.
Each MCP client maintains a connection to a single MCP server and uses contexts and capabilities from that MCP server. 
Contexts are the stream of information that flows into the language model via the server, such as database, files, application-specific information. 
Capabilities are the features an MCP server can provide, such as writing a file or running an SQL query.
Section \ref{sec:mcp_components} reviews in detail the three key components in MCP, meaning MCP host, client, and server.

    \centering

Remote MCP servers use Streamable HTTP transport and serve many clients simultaneously, while local MCP servers use the STDIO (Standard Input/Output) transport on a local machine and typically serve one client \cite{mcp_architecture}.}
    \label{fig:mcp_architecture}
\end{figure}

An important concept in MCP is primitives. 
According to the official MCP architecture documentation \cite{mcpspec2026}, primitives are the fundamental building blocks for adding contexts to the language model and enrich interactions between client, server, and language model. 
MCP specification defines three primitives that a server can expose to a client as follows: 
\begin{enumerate}
    \item Tools: Tools are functions that the LLM can invoke to take action, for example, API calls, database queries, and information search \cite{mcp_tools_2026}.
    \item Resources: Resources are data that provide contexts for the LLMs to process and they can be, e.g., API responses, code, databases, and file contents \cite{mcpspec2026resources}. 
    \item Prompts: Prompts are instructions and structured messages that describe how clients can interact with the LLMs \cite{mcp_prompts_2026}. Prompt descriptions are defined in the MCP server and can be, for example, instructions for the LLM to review code and suggest improvements.
\end{enumerate}

MCP communication has two layers \cite{mcpspec2026}: (1) a data layer that implements the JSON-RPC 2.0 based exchange protocol between client and server, including capability and version discovery, and core primitives;
(2) a transport layer that controls the connection establishment, message framing, communication, and authorization mechanisms between client and server.
This thesis focuses on the data layer of MCP, which is studied in more details in Section \ref{sec:data_layer}. 
Conceptually described in Figure \ref{fig:mcp_layers}, the data layer is the "inner" layer that implements the core protocol, while the transport layer is the "outer" layer. 
The transport layer is responsible for establishing and maintaining the connection between client and server — via STDIO for local processes or Streamable HTTP for remote ones — and handles message framing and authorization. 
The data layer, nested inside this connection, defines the actual JSON-RPC 2.0 messages exchanged between client and server, including the MCP's core primitives: tools, resources, and prompts. 
Because these primitives are defined at the data layer rather than the transport layer, they remain independent of the underlying transport mechanism, allowing the same protocol semantics to work whether client and server communicate over STDIO or over the network.
%  The separation between a data layer and a transport layer is what allows the same JSON-RPC semantics to run unchanged over a local subprocess pipe or a remote HTTPS endpoint, which is the distinction elaborated further in Section \ref{sec:mcp_workflow}.

    \includegraphics[width=0.8\textwidth]{figures/mcp_layers.png}
    \caption{MCP as a standardized protocol layer between AI applications
    and the data sources and tools they need to access, replacing
    bespoke, pairwise integrations with a single shared interface on each
    side \cite{anthropic_mcp_intro}.}
    \label{fig:mcp_layers}
\end{figure}

Unless otherwise noted, this thesis describes MCP as defined by the specification revision \textbf{2026-07-28} published on July 28, 2026. 
At the time of writing, this is the latest version and the largest revision of MCP since its introduction \cite{mcpspec2026, mcpchangelog2026}. 
Its biggest change is that MCP is now a stateless protocol: every request is self-contained and carries its own protocol version and capabilities, replacing the stateful, handshake-based session model of earlier revisions \cite{mcpspec2026}. 
Section \ref{sec:mcp_workflow} studies this change in MCP workflow and Section \ref{sec:proto-limits} discuss its consequences in detail.
This thesis follows the MCP specification's own terminology and refers to revision 2026-07-28 onwards as \emph{modern}, and to revision 2025-11-25 and earlier as \emph{legacy} \cite{mcpversioning2026}.

\subsection{Data layer of MCP}
\label{sec:data_layer}
% ============================================================
The foundation of MCP's data layer is JSON-RPC 2.0, a lightweight, stateless remote procedure call protocol using JSON format \cite{jsonrpc2020}. 
Remote Procedure Call (RPC) is a communication pattern that lets a program call a procedure running on a different process or machine using the same syntax as a local function call; the underlying protocol takes care of transmitting the call to the remote process and returning its result \cite{birrell1984implementing}. 
JSON-RPC is a lightweight realization of this pattern: each procedure call is encoded as a JSON object specifying the method name and its parameters, and each response is a JSON object containing either the method's result or an error \cite{jsonrpc2020}. 
JSON-RPC is transport-agnostic and can be carried over many different data transport protocols, including common ones such as WebSockets, HTTP/HTTPS, and Standard Input/Output. 
Because every request-response pair is self-contained at the protocol level --- carrying its own method name, parameters, and identifier (Code Block \ref{lst:jsonrpc-example}) --- JSON-RPC is stateless at the message level and leaves any session or lifecycle semantics to be layered on top by the protocol that uses it, which is exactly the role MCP's data layer plays.
\begin{lstlisting}[language=json, caption={A JSON-RPC 2.0 \cite{jsonrpc2020} request and response pair. The request object names the method to invoke (\texttt{search}) and its parameters (\texttt{query}), together with an \texttt{id} that lets the client match the eventual response to this specific call. The response shows a successful call, returning its \texttt{result} under the same \texttt{id}.}, label={lst:jsonrpc-example}]
// Request
{
  "jsonrpc": "2.0",
  "method": "search",
  "params": {"query": "cat"},
  "id": 1
}

// Response (success)
{
  "jsonrpc": "2.0",
  "result": {"matches": ["Siberian cat", "Norwegian forest cat"]},
  "id": 1
}

\end{lstlisting}
In the legacy revisions prior to the 2026-07-28 update, MCP defines a lifecycle management scheme, on top of the underlying JSON-RPC 2.0 protocol, that governs session state management and capability negotiation between MCP client and server, including which server's capabilities a client may use \cite{mcpspec2025}. 
However, in the modern (2026-07-28) revision, this scheme itself is stateless and MCP session state (previously defined in the \texttt{Mcp-Session-Id} header is deprecated. 
Each request declares its own protocol version and capabilities, and the server accepts or rejects that specific request based on whether it supports the declared version, rather than negotiating a set of capabilities once for a whole session \cite{mcpversioning2026, mcp_revision_blog}. 
Code Block \ref{lst:mcp_example} shows an example of invoking a search tool by an MCP client in the modern protocol: the request is entirely self-contained and travels on its own, defining its MCP version, client identity, and client capabilities in corresponding fields \cite{soriaparra2026spec}.
A different tool call can, in principle, be handled by a different server instance entirely, with no state shared between instances \cite{mcpchangelog2026}. 
This replaces the legacy (2025-11-25 and earlier) pattern, in which a session began with an initialized handshake that negotiated capabilities once and pinned them, together with a server-issued session identifier, for the remainder of the session \cite{mcpversioning2026}.

\subsection{MCP Core Components}
\label{sec:mcp_components}
% ============================================================
This section studies the three key components of an end-to-end MCP architecture—host, client, and server—following the latest MCP revision published on July 28, 2026. 

\subsubsection{MCP Host}
In MCP architecture, MCP host is an AI application that the end user interacts with and coordinates and manages one or multiple MCP clients \cite{mcpspec2026}.
Architecturally, the host acts as the container and coordinator for all MCP activity within the application: it creates and manages client instances and controls their connection permissions, enforces security policies
and consent requirements, and handles user authorization decisions.
Because a single host can connect to multiple MCP servers simultaneously, it is also responsible for aggregating the tools, resources, and prompt catalogues exposed by all connected servers into a unified context presented to the underlying LLM.
The host is therefore the component that decides what information is visible to the model and mediates between the model's requests to invoke tools and the policies governing which tool invocations are permitted.
Examples of MCP hosts include chat-based GenAI applications such as Claude and ChatGPT, IDE-integrated assistants such as VS Code with GitHub Copilot and Cursor. 
In the context of this thesis, the Aalto AI Assistant platform \cite{aalto_ai_assistant} acts as the MCP host for the \aitutor proof of concept described in Chapter \ref{chap:implementation}. 

\subsubsection{MCP Client}
\label{sec:mcp-client}
The host creates one MCP client for every MCP server it connects to, and each MCP client maintains a dedicated connection to a single MCP server \cite{mcpspec2026}. 
For example, in Figure \ref{fig:mcp_client}, an MCP host such as Visual Studio Code that connects to three different MCP servers needs to maintain three separate, isolated client connections. 
Since each client maintains its own connection to the corresponding server, permissions, policies, and any
per-server capability state remain isolated between a host's different client instances.

\begin{figure}[h]
    \centering
    \includegraphics[width=\textwidth]{figures/mcp_client.png}
    \caption{An IDE such as Visual Studio Code (i.e., VS Code) can be used as an MCP host. When VS Code establishes a connection to an MCP server, such as a filesystem server, the VS Code runtime instantiates an MCP client object that maintains the dedicated connection to this filesystem server. Then, when VS Code connects to another MCP server, such as a local database server, the VS Code runtime instantiates another MCP client object to manage this connection. The figure is adapted from the official MCP documentation \cite{mcpspec2026}.}
    \label{fig:mcp_client}
\end{figure}

Under the modern MCP protocol (version 2026-07-28) \cite{mcpversioning2026}, there is no session initialization handshake anymore between clieant and server.
The client now attaches its protocol version and capabilities to the field \texttt{\_meta} on every individual request it sends, and the server may accept or reject that specific request's version independently.
A client may call the server's \texttt{server/discover} method up front to know what versions and capabilities the server supports before issuing its first substantive request, but this is optional discovery rather than a
required handshake \cite{mcpversioning2026}. 
As discussed in Section \ref{sec:data_layer}, in the legacy protocol (2025-11-25 and earlier versions), a client performs the deprecated \texttt{initialize} handshake instead, which negotiates capabilities once and pins them for the lifetime of that session \cite{mcpversioning2026, mcpclient2026}. 
In modern and legacy revisions of MCP, the client is still the channel through which the host forwards tool invocations, resource requests, and prompt requests to the server, and through which the server's responses and notifications are relayed back to the host \cite{mcpclient2026}.

\subsubsection{MCP Server}
\label{sec:mcp-server}
An MCP server is a program that exposes specific capabilities to MCP clients through the standardized MCP primitives, including tools, resources, and prompts \cite{mcpserver2026}.
MCP servers can be deployed in two modes that differ substantially in their operation.
Local MCP servers can interact with local filesystems \cite{ray2025survey}.

An AI application can connect to both local and remote MCP servers, which differ substantially in their operations.

\paragraph{Local MCP Server}
A local MCP server runs as a subprocess on the same machine as the host and communicates with its client exclusively through standard input and output (STDIO) transport \cite{mcpspec2026}.
For example, Claude Desktop application can connect to the official Filesystem MCP Server \cite{mcpfilesystem2026} as a local subprocess, giving the host controlled, approval-gated access to files on the user's machine \cite{mcplocalservers2026}.
Because the server process is spawned and supervised by the host, its source code or binary is present on the user's machine and can in principle be inspected, version-pinned, or sandboxed by the operating system before execution \cite{park2026attacksurface}.
This makes local MCP servers well-suited to connect to resources that are inherently local to the user's environment, such as a filesystem, a local Git repository, or an on-premises database, and to let developers experiment with MCP rapidly.
In the official documentation of MCP, local servers are adopted by many official reference MCP servers, such as the Git MCP server \cite{mcpexamples2026}.
On the other hand, the primary limitation of local servers is scalability.
Since the server process is spawned and owned by a single host process, one STDIO server instance serves one client at a time, regardless of whether the underlying protocol revision is stateful or stateless \cite{mcpspec2026, mcpstdio2026}.
Scaling to many concurrent users still requires spawning one server process per user, which makes the local transport unsuitable for an organization-wide system serving many concurrent users simultaneously.
 
\paragraph{Remote MCP Server}
A remote MCP server is hosted on an infrastructure separate from the user's machine and communicates with the MCP client over a network connection, most commonly using the Streamable HTTP transport \cite{mcpspec2026}.
Streamable HTTP exposes the server through a single unified HTTP endpoint over which the client can send requests and receive both standard HTTP responses and streamed server notifications, enabling efficient bidirectional communication without requiring a persistent socket connection.
Unlike a local server, a remote MCP server can serve many clients concurrently. 
Therefore, a remote MCP server with Stremable HTTP transport is suitable for deployment of an organization-wide GenAI
assistant serving many simultaneous users \cite{mcpremoteservers2026}.
Under the modern MCP revision, this scalability advantage is reinforced further at the transport level.
Because the latest MCP revision removes protocol-level sessions and the \texttt{Mcp-Session-Id} header used by earlier revisions, client's requests are no longer pinned to the server instance that handles the initial handshake \cite{mcpspec2026, mcp_revision_blog}. 
As a result, described in Figure \ref{fig:stateless-topology}, any client's request can land on any server instance behind a round-robin load balancer, instead of being directed to the same server instance in the sticky sessions.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.9\textwidth]{figures/stateless-topology.pdf}
    \caption{Topology of MCP's core protocol before and after the removal of protocol-level sessions in the July 28, 2026 revision. Under the previous session-based model (left), a client's requests were pinned to a single server instance via a sticky
    route, requiring a shared session store across instances. Under the
    stateless model (right), the load balancer can route any request to any
    server instance, since no session state is tied to a specific instance.

This scalability advantage comes at the cost of introducing authentication, authorization, and multi-tenancy concerns that the base MCP specification delegates to server developers, as discussed further in Chapter \ref{chap:challenges}.

Under the modern protocol specification, a server's capability set is no longer negotiated once at the start of the session; instead, each client's incoming request declares the protocol version and capabilities it needs, and the server responds accordingly \cite{mcpspec2026, mcpversioning2026}.
In stead, a server's capabilities can be found up front through the discovery phase—this is studied more in Section \ref{sec:mcp_workflow}.
For servers that still use legacy revisions (2025-11-25 and earlier), they negotiate the capabilities once during the initial handshake~\cite{mcpversioning2026}.
Due to the scope of this thesis, the compatibility and interoperability behaviors between modern and legacy client and server are not covered in detail; they are described in the official MCP versioning documentation \cite{mcpversioning2026}.

\subsection{MCP Workflow}
\label{sec:mcp_workflow}
% ============================================================
%An MCP workflow answers a single question: when, and how often, do a client and server establish what they mutually support before they can safely exchange a message?
At its core, an MCP interaction follows a simple pattern: a client sends a JSON-RPC \emph{request} specifying which method to invoke and what parameters to pass it, and the server sends a \emph{respond} with a message containing either the method's result or an error \cite{mcpspec2026}. 
That is, in an MCP workflow, a client and a server share an understanding of what each of them supports, including protocol version and capabilities, before they can safely exchange a message. 
MCP legacy (2025-11-25 and earlier) and modern (2026-07-28) revisions still share the same core request/response exchange. 
However, they differ substantially in how a connection is established and maintained, and how a server asks a client for something mid-call. 
%Every other detail of the workflow — including whether there is a distinct setup phase, whether capabilities are pinned for a whole connection or re-declared per request, and how a multi-step operation keeps track of where it is — follows how often the mutual client-server understanding is established.
%Everything the protocol does, from listing available tools to invoking one, is built on top of this same request/response exchange.

\paragraph{Legacy workflow.} The workflow of legacy MCP revisions can be described as a three-phase lifecycle, i.e., initialization, operation, termination \cite{mcpspec2025}, which remains relevant for interoperability with legacy servers still-deployed. 
The workflow opens every connection with a handshake that fixes the protocol version and capabilities for the session as a whole, so that no later message needs to renegotiate them.
As Figure \ref{fig:legacy_workflow} shows, a session opens with an \emph{initialization phase}: the client sends an \texttt{initialize} request that contains the its protocol version and capabilities; 
the server replies with the protocol version and capabilities it supports, together with a session identifier returned in the \texttt{Mcp-Session-Id} header as metadata;
and the client confirms with an \texttt{initialized} notification to indicate that it is ready for operation
The session identifier header scopes every subsequent message to this one negotiated session.

Then, every subsequent message during the \emph{operation phase} is exchanged under the capability set fixed by the initialization handshake; 
no message needs to re-state the successfully negotiated protocol version or capabilities, because the connection itself already carries that context. 

The session ends with an explicit \emph{shutdown phase}: the client disconnects, and the connection is closed. 
This legacy MCP workflow reflects a conventional stateful network session, and it is efficient precisely because the negotiation happens only once.
On the other hand, the cost is that the server must hold connection-scoped state for as long as the session lasts, and that state ties a single client to the specific server instance that handled its handshake \cite{mcpversioning2026, soriaparra2026spec}.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{figures/legacy_workflow.png}
    \caption{Legacy (2025-11-25 and earlier) MCP workflow: a single
    initialization handshake fixes the protocol version and capabilities
    for the entire session, which subsequently ends with an explicit
    shutdown \cite{mcpspec2025}.}
    \label{fig:legacy_workflow}
\end{figure}

\paragraph{Modern workflow.} The 2026-07-28 revision replaces the legacy session-based model with a stateless protocol core: the \texttt{initialize}/\texttt{initialized} exchange and the \texttt{Mcp-Session-Id} header are retired entirely.
As Figure \ref{fig:modern_workflow} shows, capability discovery is now optional in the modern MCP revision: it becomes an ordinary RPC method called \texttt{server/discover}, rather than being negotiated once during a connection handshake \cite{soriaparra2026spec}. 
A client may call this method at any point to learn what tools, resources, and prompts a server exposes, but doing so is no longer a precondition for making other requests.
Thus, if a client already knows what it needs, it can skip discovery and
call \texttt{tools/call} method directly to invoke a server's tool. 
In addition, because \texttt{server/discover} method is stateless and cacheable, its response payload has a Time-To-Live \((\texttt{ttlMs})\) parameter and a defined cache scope. % TODO: add code block
This structural design permits clients to locally persist server's capabilities across multiple executions, effectively eliminating the network overhead of redundant discovery probes on successive requests \cite{soriaparra2026spec}.
  
In the workflow of modern MCP revision, operation no longer relies on a capability set fixed earlier in the connection. 
Instead, the client attaches its desired protocol version and capabilities in the \texttt{\_meta} field of each request it sends. 
That is, each request is self-contained. 
If the server supports what is declared, it simply returns a result, exactly
as it would to any other request; if not, it returns an \texttt{UnsupportedProtocolVersionError}, and the client retries the same request with a version it knows the server supports \cite{mcpversioning2026}. 

Finally, the shutdown phase is no longer applicable in modern MCP revision because because there is no session state to release.
Instead, a client simply stops sending requests, and closing the underlying transport connection (if one was open at all) is a transport-level event, rather than a protocol-level one \cite{mcpversioning2026}. % The legacy explicit shutdown that releases session state has no equivalent in the modern protocol.
This modern MCP workflow is consistent with the design principle that no request should depend on state established by an earlier one.
As discussed in Section \ref{sec:mcp_components}, since no request depends
on connection-scoped state set up by an earlier request, any request can be
answered by any server instance, which is what makes stateless, round-robin deployment possible \cite{mcpchangelog2026}.

    \centering
    \includegraphics[width=\textwidth]{figures/modern_workflow_light.png}
    \caption{Modern (2026-07-28) MCP workflow: protocol version and capabilities are declared per request via \texttt{\_meta}; an unsupported version yields an explicit error rather than blocking the connection, and the client retries with a mutually supported version. Adapted from the official MCP documentations \cite{mcpversioning2026, soriaparra2026spec}.}
    \label{fig:modern_workflow}
\end{figure}

\textbf{State across requests.} A consequence of removing the session is that a multi-step operation can no longer implicitly track its own progress; for example, a shopping cart, an open browser context, or a database transaction can no longer be remembered by the server simply because ``the client is still connected'' \cite{mcp_tools_2026}. 
Figure \ref{fig:handle_pattern} shows that under the modern workflow, a server that needs this kind of continuity instead mints an explicit handle from one call, for example, a \texttt{basket\_id}, which the client threads back as an ordinary argument on subsequent calls that continue the operation, making state visible in the model's own reasoning trace rather than hidden inside the connection \cite{mcp_revision_blog}.

\textbf{Mid-operation input with MRTR.} A related consequence for the modern MCP concerns how a server asks a client for input mid-call, for example, to elicit a missing parameter. The legacy model handles this by having the server send a request back to the client over a held-open bidirectional stream. 
Meanwhile, the modern revision replaces this with \emph{Multi Round-Trip Requests} (MRTR) because there is no persistent connection to hold open: the server terminates the original request with an \texttt{InputRequiredResult} specifying what it needs, and the client resubmits the original call --- as a new, independent request --- with the requested input attached \cite{mcpspec_mrtr}.

The AI Tutor proof of concept presented in Chapter~\ref{chap:implementation} is built against a session-based, legacy
revision of MCP, since the modern revision had not yet been published at the time that implementation work was carried out. Section \ref{sec:implementation-limitations} discusses this gap and its consequences for the proof of concept in more detail.

\subsection{Current Ecosystem of MCP}
\label{sec:mcp-ecosystem}
% ============================================================

%The emergence of Gen AI tools in recent year has accelerated a new paradigm of interactive and tailored AI agents that focus on a specific, tailored application. FastMCP’s OpenAPI converter has become one of the most popular tools for auto-generating MCP servers from REST APIs.
Since the public release of MCP in November 2024, a large and rapidly growing ecosystem of tooling, server implementations, and client integrations has formed around the technology.

On the tooling side, MCP's official software development kits (SDKs) support multiple common programming languages, including TypeScript, Python, Java, and C\#, reflecting the protocol's uptake across diverse development ecosystems.
Handy software development frameworks such as FastMCP \cite{fastmcp2026} have substantially lowered the barrier to creating new MCP servers.
For instance, FastMCP's OpenAPI converter \cite{fastmcp_openapi2026} can automatically generate a working MCP server from an existing REST API specification, so that organizations with established API infrastructure can expose their services to LLM agents without writing MCP-specific server code from scratch.
The FastMCP framework is also used to develop the \aitutor agent in Chapter \ref{chap:implementation} as the proof-of-concept implementation for this thesis. 

On the enterprise adoption side, industry growth has been rapid.
Major technology companies including Microsoft \cite{microsoft_mcp_governance2026}, Google \cite{google_mcp2026}, Figma \cite{figma-mcp}, and GitHub \cite{github-mcp-server} have adopted MCP for engineering and productivity workflows.
Public server registries track the resulting expansion.
Community-run indexes such as the Glama AI registry \cite{glama_mcp_servers_2026} list tens of thousands of community-contributed and official MCP servers as of mid-2026, spanning categories from developer tools, databases, and filesystems to finance, browser automation, and research data. Anthropic has also since launched an official MCP Registry (at \texttt{registry.modelcontextprotocol.io}) as a namespace and publish/discovery service for the ecosystem \cite{mcpregistry2026}. However, as discussed in Section~\ref{sec:proto-limits}, it functions as a discovery index rather than a security-vetting gate.

As organizations have moved from individual and ad hoc MCP connections toward managing many MCP servers across teams, a \emph{gateway} pattern has emerged as a common architectural response: an MCP gateway sits as a reverse proxy between the AI host and the servers it uses, centralizing authentication, policy enforcement, and observability rather than distributing these concerns across every individual server. This pattern is directly relevant to the design of the \UniMCP framework described in Chapter~\ref{chap:design}, as it offers a concrete answer to the scalability and governance requirements the university context imposes.

\section{Challenges of MCP and Research Gap}
\label{chap:challenges}
% ============================================================

MCP has been adopted at significant scale since its introduction in November 2024, but its deployment in organizational, enterprise production environments has exposed a layered set of challenges.
To reason precisely about these challenges, this chapter distinguishes three origins: (1) limitations inherent to the MCP specification itself (Section \ref{sec:proto-limits});
(2) problems that have emerged in the current ecosystem of MCP implementations and registries (Section \ref{sec:ecosystem-challenges}); and 
(3) requirements that arise specifically from adopting MCP in education institutions settings (Section \ref{sec:university-context}).
This three-way distinction is essential in the thesis because each origin motivates a different category of design decisions in the \UniMCP framework described in Chapter \ref{chap:design}: 
protocol-level limitations identify controls that the framework can \emph{add} to what the spec provides; 
ecosystem challenges identify what the framework must \emph{guard against} at runtime; and
university-context requirements identify the \emph{policies and standards} those controls must satisfy.

\textbf{Threat analysis method.} Rather than applying a single, general-purpose threat-modeling framework such as STRIDE or MAESTRO, each of the three challenge layers is analyzed using evidences appropriate to its origin: official MCP specification, published empirical studies of deployed MCP servers, and applicable regulation and institutional policy.
Protocol-level limitations (Section~\ref{sec:proto-limits}) are identified through direct analysis of the official MCP specification, checking what the protocol does and does not mandate. 
Ecosystem-level challenges (Section~\ref{sec:ecosystem-challenges}) are synthesized from published security studies of deployed MCP servers, benchmarked attacks, and documented real-world incidents, organized using the threat categories proposed by Narajala and Habler~\cite{narajala2025enterprise}. 
University-context requirements (Section~\ref{sec:university-context}) are derived from applicable regulation (GDPR) and institutional policies of \aalto, supplemented by published research on GenAI governance in higher education. 
This threat analysis method ensures that every threat or requirement carried forward into Chapter~\ref{chap:requirements} is traceable to a specific, citable origin rather than to the author's own judgement alone.

% ------------------------------------------------------------
\subsection{Protocol-Level Limitations}
\label{sec:proto-limits}
% ------------------------------------------------------------

Protocol-level limitations are structural properties of the MCP specification as designed \cite{mcpspec2026}.
They are not failures of any particular implementation; they are deliberate design choices that maximize
flexibility at the cost of leaving specific security and multi-tenancy properties entirely to the
developer \cite{yan2025mcpmisuse, hou2025landscape, narajala2025enterprise}.

\textbf{No mandatory authentication or authorization.}
The MCP specification recommends that remote MCP servers using the Streamable HTTP transport follow OAuth 2.1, but at the protocol layer it does not mandate any specific, strict authentication mechanism and provides no authorization enforcement \cite{mcpspec2026, mcp_authorization_2025, mcp_streamable_http}.
Therefore, a server that omits authentication entirely is still compliant with the MCP specification.
This means the protocol level itself cannot prevent an unauthenticated client from discovering and invoking
a server's tools if the server's operator neglects to implement access controls.
Because authorization is optional at the protocol level, the responsibility for authenticating clients and authorizing tool access falls to individual server operators \cite{narajala2025enterprise, owasp_mcp_security_2026}.

\textbf{No protocol-level transport security.}
The MCP application layer remains entirely decoupled from transport security mechanisms. The specification defines how messages are framed and structured using JSON-RPC, but it mandates no native protocol-level mechanisms to negotiate, verify, or enforce cryptographic security between a client and a server \cite{mcpspec2026}. When using remote transport variants, such as Streamable HTTP, transport security (TLS/HTTPS) is an architectural deployment requirement rather than an intrinsic property enforced by the MCP engine itself. 
Consequently, developers must rely on external infrastructure—such as reverse proxies, API gateways, or application-level network stacks—to secure the underlying transport channel \cite{mcp_streamable_http, owasp_mcp_security_2026}.

\textbf{Free-form tool descriptions.}
MCP tool descriptions are arbitrary natural language strings with no structure, length limit, or semantic
constraint imposed by the MCP specification \cite{mcpspec2026}.
This is a deliberate flexibility decision, but it also makes MCP systems prone to tool poisoning attacks—a cybersecurity attack that happens when malicious instructions embedded in a tool's description \cite{hasan2026mcp}. 
Since the LLM processes tool descriptions as a part of its necessary context, the poisoned description acts as a command to manipulate the model's behavior, leading to adversarial attack such as hijacking the functions of other trusted tools or exposing personal, sensitive data \cite{wang2026mcptox}.
For instance, if an MCP server has a tool with file writing permission, its LLM can be manipulated to add malicious code snippets in the \texttt{.bashrc} file to open a backdoor port for attacker \cite{radosevich2025mcp}.

\textbf{Deficient server vetting and registry governance.}
The specification mandates no default mechanism for verifying the provenance, integrity, or reliability of an MCP server before a client connects to it \cite{mcpspec2026}. 
As introduced in Section \ref{sec:mcp-ecosystem}, Anthropic has since launched an official MCP Registry at \texttt{registry.modelcontextprotocol.io} as a namespace and discovery service for publishing and
finding servers; however, it functions as a publish and discovery index rather than a security gate, and listing a server does not require independent security review or a verified-publisher certification analogous to a code-signing authority. There is still no concept of a verified publisher identity tied to an audited source, nor a protocol-level revocation mechanism reachable from the client. Which MCP servers to trust depends on the MCP host operator.

\textbf{No built-in tenant isolation.}
As discussed in Section~\ref{sec:mcp_workflow}, the modern (2026-07-28) revision removed the stateful, session-based model of earlier revisions in favor of self-contained requests. Legacy revisions are built around a session-based protocol between a client and a server, with no built-in primitive for namespacing a session or separating one user's context from another's within a shared
server process; multi-tenancy had to be implemented entirely outside the protocol layer \cite{mcpversioning2026}. 
The modern revision instead carries a state as an explicit, server-minted handle passed back as an ordinary tool argument (Figure~\ref{fig:handle_pattern}) \cite{mcp_revision_blog}. This resolves the scalability problem the legacy session model created, but it does not, by itself, guarantee tenant isolation: because a handle is just a value the client supplies like any other argument, the specification provides no protocol-level check that a handle issued for one authenticated user cannot be supplied, accidentally or maliciously, under a different user's request. 
Whether a handle-based resource is re-verified against the requester's identity on every use, or is trusted merely because the client possesses it, is left to the MCP server implementation.

\subsection{Ecosystem-Level Challenges}
\label{sec:ecosystem-challenges}
% ------------------------------------------------------------

Ecosystem-level challenges are problems that emerge not from the protocol specification, but from the current state of
how MCP systems are built, deployed, and maintained.
They are empirically observable in deployed servers and would persist even if all operators were fully aware of the protocol-level limitations above.

\textbf{Widespread security vulnerabilities in open-source servers.}
Hasan et al.\ conduct a large-scale empirical evaluation of MCP server security across 1,899 open-source servers and find that 7.2\% contain at least one detectable security vulnerability \cite{hasan2025mcp}.
This study also discovers that the most common vulnerability class is credential exposure, e.g., hardcoded API keys and passwords in source code, which affects 3.6\% of servers.
In addition, lack of access control affects 1.4\%, and transport security issues such as SSL verification bypasses affect 0.7\%.

\textbf{Tool poisoning in deployed servers.}
The same empirical study conducted by Hasan et al. \cite{hasan2025mcp} also finds that 5.5\% of the analyzed MCP servers are affected by tool poisoning, which involves malicious instructions embedded in tool descriptions that direct the LLM to perform unintended actions that lead to credential theft and malicious code execution. 
%Tool poisoning in indirect prompt injection. Prompt injection is a major cybersecurity threat that allows attackers to hijack or manipulate agent's behavior. The attackers can input malicious instructions in their prompts or external data sources such as documents and websites. 
In another study in 2025, Wang et al. develop MCPTox, a benchmarking tool to systematically evaluate robustness of 20 prominent LLMs against tool poisoning in real-world MCP servers \cite{wang2026mcptox}.
This study confirms that these LLMs are broadly susceptible to tool poisoning: the highest attack success rate reaches 72.8\% with the o1-mini model, while the highest attack refused rate is just below 3\% with the Claude-3.7-Sonnet model.

\textbf{Post-deployment mutation attacks.}
Bhatt et al.\ document a qualitatively different threat: the rug pull attack, in which a server that behaves correctly at installation time is later silently modified, leading to changes in its tools and behaviors \cite{bhatt2025etdi}.
A real-world rug pull attack happened in 2025, when an unofficial Postmark MCP server with over 1,500 weekly downloads was modified to exfiltrate user emails to attacker address, remaining undetected for several weeks \cite{postmark2025incident}.
This threat is structurally enabled by the protocol's lack of MCP server integrity guarantees discussed in Section~\ref{sec:proto-limits}.

\textbf{Cryptographic misuse.}
Yan et al.\ apply MICRYSCOPE, the first static analysis framework targeting cryptographic misuse specifically in MCP servers, and find widespread ad hoc practices across deployed servers, including weak hash functions used for password storage and missing authentication \cite{yan2025mcpmisuse}.
Because the MCP specification imposes no cryptographic requirements, these practices arise from individual developer decisions without any protocol-level safety net.

\textbf{Immature enterprise tooling.}
Most reference, community MCP servers default to the STDIO transport, which imposes a one-process-per-session architecture that is not suitable for concurrent organizational deployment \cite{descope2025enterprise}.
Enterprise-grade capabilities --- including OAuth~2.1 compliance, SSO integration, centralized audit logging, and granular
per-user permissions --- are absent from most server implementations and must be built independently by each operator \cite{narajala2025enterprise}.

\textbf{Public registries not reviewed.}
Public MCP registries such as Glama list tens of thousands of servers contributed by anonymous or pseudonymous authors without
systematic security review~\cite{glama_mcp_servers_2026}.
Moreover, because integrating an AI host with a remote MCP server via HTTP transports requires only a URL, a single compromised MCP server can affect a large population before any registry-level intervention. 

% ------------------------------------------------------------
\subsection{University-Context Requirements}
\label{sec:university-context}
% ------------------------------------------------------------

University-context requirements are constraints that arise from the specific regulatory, institutional, and operational environment of typical higher education institution.
They need to be addressed even if the protocol-level limitations in Section \ref{sec:proto-limits} and ecosystem-level challenges in Section \ref{sec:ecosystem-challenges} are fully resolved.

\textbf{Data protection regulation.}
Higher education institutions around the world must adhere to the local regulatory frameworks to safeguard data privacy.
For instance, European universities are subject to the General Data Protection Regulation (GDPR), which governs the collection, processing, storage, and transfer of personally identifiable data \cite{gdpr2016}.
Student academic records, such as transcripts, enrollment history, and grades, are personal data under GDPR and are subject to the principles of data minimization, purpose limitation, and storage limitation \cite{ng2025security}.
A recent study of GenAI usage guidelines at 43 universities across 12 countries finds that GenAI introduces privacy risks not addressed by existing security frameworks of these universities, including the risk of inferring or
exposing sensitive personal information beyond what a user directly discloses \cite{ng2025security}.

\textbf{Institutional data classification.}
Educational institutions maintain their data classification hierarchies because legal frameworks such as GDPR define obligations for personal data, and because these institutions need to handle different kinds of data such as research publication, financial records, exam materials, and network credentials.
For example, Aalto University classifies information as public, internal, confidential, or secret \cite{aalto_classification_info}.
In the context of the \aitutor use case (Section~\ref{sec:aitutor-use-cases}), student data, such as
email addresses, student numbers, and transcripts, fall under the confidential tier, while the course information
catalog is public.
That means that an MCP integration must enforce these tiers at the tool response layer so that confidential data is
handled differently from internal and public data, and secret data should never be processed by a GenAI system.

\textbf{Institutional identity and SSO.}
University services are identity-bound: access to a student's transcript is tied to that student's institutional identity, which is typically managed by the university's identity authentication provider.
Therefore, an MCP integration must integrate with the university's existing identity infrastructure and propagate the verified institutional identity through the tool call chain so that server-side data scoping can enforce ownership.

\textbf{Multi-role user population.}
A university's user population is not homogeneous.
Students, teaching staff, research staff, administrative staff, and IT personnel typically hold different access rights to institutional systems.
An MCP integration must support role-based access control that reflects these distinctions, preventing,
for example, a student from invoking a tool that an academic advisor could legitimately use to access records of other students. 

\textbf{Institutional audit accountability.}
Universities are subject to governance requirements and potential regulatory audits beyond those of a typical consumer product.
Access to student personal data must be logged in a tamper-evident, user-attributable form, retained for institutionally defined periods, and available for compliance reporting.
This is a stricter requirement than general-purpose application logging.

\subsection{Research Gap}
\label{sec:research-gap}
% ------------------------------------------------------------

The three challenge layers identified in this chapter combine into a research gap.
At the protocol level, while the MCP specification outlines OAuth 2.1 for remote endpoints, it treats authentication as structurally optional, meaning default implementations can operate without mandatory authentication or strict transport layer enforcement; furthermore, MCP provides no native tool description constraints or server vetting mechanisms (Section \ref{sec:proto-limits}). 
At the ecosystem level, deployed servers exhibit widespread cybersecurity risks, including credential exposure, tool poisoning, and post-deployment mutation in registries that provide no systematic governance.
At the university-context level, data protection regulation, institutional data classification, identity-bound SSO, multi-role
access control, and audit accountability impose requirements that go beyond what MCP and its current ecosystem provide.

\textbf{No existing work addresses all three layers of challenges together in a university GenAI production context.}
Table~\ref{tab:gap-analysis} presents the four most directly relevant prior works against these three challenge layers.

    \item Ng et al.~\cite{ng2025security} establish the university-context requirements for GenAI systems but do not address MCP.

\subsection{GenAI in University Contexts}
% This subsection should bridge the background chapter to the \UniMCP framework.
Universities need to process large volumes of sensitive personal data as a routine part of their operations, spanning study planning, course enrollment, transcripts, advising, and broader administrative workflows. 
Therefore, GenAI assistants deployed for university users need stricter governance and control than general-purpose chatbots, because a single compromised data integration could expose private education records or emails \cite{ng2025security}.
For European universities as \aalto, the General Data Protection Regulation (GDPR) governs how any personally identifiable student data may be collected, processed, and retained, \cite{gdpr2016}) --- that includes data existing temporarily in an LLM's context window during a tool-mediated interaction.
A recent qualitative analysis of GenAI usage guidelines from universities across 43 universities across 12 countries finds that institutions broadly acknowledge privacy and security risks posed by GenAI, but that existing regulatory frameworks fall short of addressing specific threats imposed by GenAI \cite{ng2025security}.
For example, a model's capacity to infer sensitive personal attributes indirectly from a student's language patterns, without
ever accessing a formal education record.
This implies that governance of an university GenAI system requires controls that go beyond regulatory compliance alone.
Therefore, the analysis recommends GenAI-specific risk assessment frameworks and technical safeguards tailored to academic contexts \cite{ng2025security}.

\subsection{Research Questions}

The challenges identified in Section \ref{chap:challenges} show that MCP leaves authentication, transport security, and server vetting unresolved at the protocol level, that these gaps are exploited in practice at the ecosystem level, and that university deployment adds regulatory and identity requirements on top. No existing framework addresses all three layers together for a university GenAI production system. Therefore, this research gap strongly motivates three research questions:
 
\begin{enumerate}
    \item \textbf{What are the main security threats when integrating MCP into a production-level university GenAI system?}
    \item \textbf{How can a secure MCP integration layer be designed to mitigate these threats?}
    \item \textbf{How effective is the proposed system?}
\end{enumerate}
 
Research question (RQ) 1 concerns identifying and characterizing the concrete security threats --- at the protocol, ecosystem, and university-context levels --- that arise when MCP is integrated into a university GenAI production system, and is addressed by the threat analysis in Chapter~\ref{chap:challenges}.
RQ2 concerns how a layer of security controls can be designed, on top of MCP, to mitigate the threats identified under RQ1, and is addressed by the requirements derived in this chapter and the design presented in Chapter~\ref{chap:design}.
RQ3 concerns whether the resulting design, once implemented, actually closes the threats it is designed against, and is addressed by implementing the design as the \aitutor proof of concept (Chapter~\ref{chap:implementation}) and evaluating it against established, independent security-testing methods (Chapter~\ref{chap:evaluation}).
All three questions are answered together through the design, implementation, and evaluation of a single artifact, \UniMCP, instantiated through the \aitutor proof of concept.

\subsection{Requirements for \UniMCP}
\label{sec:requirements}
% ------------------------------------------------------------

The requirements for \UniMCP are mainly derived from the architecture and challenges of MCP identified in Chapter \ref{chap:challenges}, the operational context of Aalto AI Assistant described in Section~\ref{sec:aalto-ai-assistant},  and the AI Tutor use case defined in Section~\ref{sec:aitutor-use-cases}.
The requirements are organized into two categories: functional and security. Because this thesis
narrows its scope to the security of an MCP integration (RQ1--RQ3), a property that was earlier framed
as a separate scalability requirement --- isolating concurrent user sessions from one another --- is
instead framed here as a security requirement (SR7), since a failure to isolate sessions correctly
under concurrent load is fundamentally a confidentiality and authorization failure, not merely a
performance one.

% ·····················
\subsubsection{Functional Requirements}
% ·····················
The functional requirements define what \UniMCP must take into account in order to support MCP integration into the IT production systems of a university.
 
\textbf{FR1 --- University Identity Integration.}
\UniMCP must authenticate users via the university's identity provider before any MCP tool is invoked.
The authenticated identity must be propagated to individual MCP servers so that tool handlers can make identity-aware access decisions. 
For example, the student study transcript must be only accessible to the transcript's owner.

\textbf{FR2 --- Gateway Mediation.}
All tool invocations from MCP host to MCP servers must be routed through a central gateway, i.e., an enforcement point for authentication, authorization, and logging.
This follows the gateway architectural pattern identified in Section \ref{sec:mcp-ecosystem} as the ecosystem's primary response to the multi-tenant MCP governance gap.

\textbf{FR3 --- User Consent Enforcement.}
Before any tool that accesses personal data is invoked, the gateway must ensure that the user has given their consent to that access during the current session, in line with the MCP specification's requirement that the host handles user authorization decisions \cite{mcpspec2026} and with GDPR's requirement for freely given, specific, and informed consent.

% ·····················
\subsubsection{Security Requirements}
% ·····················
The security requirements respond directly to the ecosystem-level threats catalogued in Section \ref{sec:ecosystem-challenges}: credential exposure, tool poisoning, and post-deployment mutation are not hypothetical risks but empirically observed failure modes of deployed MCP
servers \cite{hasan2025mcp, wang2026mcptox, park2026attack}, and the threat categories identified by
Narajala et al. \cite{narajala2025enterprise} are used to organize them.
%In addition, MAESTRO threat modeling framework is also consulted to form the security requirements in \UniMCP presented as follow. 

% How to avoid identity spoofing? 
\textbf{SR1 --- Authentication}
\label{sec: SR1}
Every request that reaches an MCP server, directly or through the gateway, must carry a valid credential. 
A request without a valid, unexpired token must be rejected before any tool invocation.
This requirement directly closes the protocol-level gap identified in Section~\ref{sec:proto-limits}: the MCP specification recommends, but does not mandate, authentication for remote
servers~\cite{mcpspec2026}, so a compliant server can legally omit it. \UniMCP treats authentication as
non-optional rather than leaving it to individual server implementations.

\textbf{SR2 ---  No Sensitive Data Exposure to LLM.}
\label{sec: SR2}
Any operation that involves university user's sensitive data or identity must not be an MCP tool, because a tool enable models to interact with external systems, such as querying databases, calling APIs. 
They must be implemented as a internal service call that executes deterministically outside the LLM's tool-selection loop, rather than as an MCP tool the model chooses whether and when to invoke. 
These operations are, for example, mapping an authenticated, logged-in user to a student number or accessing a student's transcript.
Only operations on non-identity-bound, lower-sensitivity data (e.g., course catalogue search or research publication search) should be exposed to the LLM as an MCP tool.
This requirement follows directly from the tool poisoning findings of Section~\ref{sec:ecosystem-challenges}, because a poisoned or compromised MCP tool can influence \emph{whether} and
\emph{how} the model decides to call it~\cite{wang2026mcptox}. Keeping identity resolution and
access-control decisions on the internal, non-LLM-mediated code path means that even a successful
prompt injection or tool-poisoning attack against the course-recommendation tool cannot, by itself,
grant access to another student's data, because that decision was never delegated to the model in
the first place.

\subsection{Principles of \UniMCP}
\label{sec:principles}
The design of \UniMCP is guided by seven principles that translate the requirements of Chapter~\ref{chap:requirements} into concrete architectural decisions. 
Each principle names the requirement(s) it operationalizes so that the traceability established in Section \ref{sec:rd-req-derivation} continues into the design itself.
 
\textbf{P1 --- University-Identity-First (FR1, SR2).}
Every MCP request must be associated with an authenticated university user before any tool executes.
Identity is established once, at the boundary between the MCP host and the university's identity authentication provider, and is propagated through every subsequent internal call.
 
\textbf{P2 --- Least Privilege (SR4).}
An MCP component should only receive the  bare minimum data it needs to complete its specific task, and nothing more. 
For instance, in an MCP tool that recommends courses tailored to a certain student, the LLM should only receive relevant course information and necessary student's study history, rather than the attendance list of courses or the student's identity records.
 
\textbf{P3 --- User-Scoped Authorization (FR1).}
Authorization decisions are always scoped to the requesting user's own data: a student can retrieve
only their own transcript, never another student's, and this scoping is enforced on the internal
service path rather than left to the LLM's judgement.
 
\textbf{P4 --- Gateway-Mediated Tool Approval (FR2, ScR1).}
All tool invocations are routed through a single enforcement point --- the gateway --- which maintains the catalogue of approved tools available to the AI assistant. 
A tool that is not registered at the gateway is not reachable by the agentic pipeline, regardless of what the remote MCP server exposes. 
This is also what makes tool extensibility (ScR1) possible without redesigning the pipeline: adding a tool means registering it at the gateway and at the MCP server, not modifying the
orchestration logic that calls the gateway.
 
\textbf{P5 --- Internal-Path Priority for Identity-Sensitive Operations (SR1).}
Operations that resolve or depend on institutional identity are implemented as internal service
calls on a deterministic code path, outside the set of tools the LLM is allowed to select. Only
lower-sensitivity, catalogue-style operations are exposed to the LLM as MCP tools. This is the
architectural expression of SR1 and is detailed in Section~\ref{sec:architecture}.
 
\textbf{P6 --- Auditability (institutional audit accountability, Section~\ref{sec:university-context}).}
Every tool call and every internal identity-resolution call is logged with the requesting user's
identity, the resource accessed, and a timestamp, so that access to student data can be reconstructed
for security review or institutional compliance reporting.
 
\textbf{P7 --- Untrusted-Data Boundary (prompt-injection resistance, ecosystem-level challenges,
Section~\ref{sec:ecosystem-challenges}).}
Any content that originates outside the gateway's own system instructions --- tool responses,
retrieved documents, external API payloads --- is treated as untrusted data and is never allowed to
be interpreted as a system-level instruction, regardless of its apparent formatting.

\subsubsection{MCP host}
The MCP host is the AI application backend: the existing FastAPI application (\texttt{main.py}) delegates
student-facing requests to the \textbf{AI Tutor router} (\texttt{/api/v1/student/query}), which embeds
the \textbf{MCPAgentPipeline}, an agentic pipeline built with Haystack. The pipeline itself plays the
role of the MCP \emph{client}: its \texttt{ToolInvoker} component opens and manages the connection to
the remote MCP server and issues tool calls on behalf of the current user's authenticated session.
Placing the MCP client inside the pipeline that Aalto AI Assistant already uses for chat completion
(rather than introducing a new, separate host application) follows the least-disruption rationale
behind P4: the production chat pipeline, reverse proxy, and front end are reused unchanged, and only
the AI Tutor router and the pipeline's tool-calling branch are new.
 
\subsubsection{MCP server}
The MCP server is a dedicated, remotely deployed \textbf{AI Tutor MCP server} that exposes the
course-search capability as an MCP tool and connects to the SISU Course APIs on the university's
behalf. Two design decisions shape this component. First, only the course-search capability is
exposed as an MCP tool; the transcript-retrieval and student-identity-resolution capabilities are
deliberately \emph{not} exposed through MCP at all, but implemented as internal calls from the AI
Tutor Service to the SISU transcript endpoint and to the User Service (P5, SR1) --- this is the
concrete architectural realization of internal-tool priority. Second, the server authenticates its
outbound calls to the SISU Course APIs using a service-level token issued by the university's API
management platform (3scale), so that the remote MCP server itself never handles end-user
credentials directly; it operates within a trust boundary already established by the university's
existing API gateway infrastructure.
In \aitutor, a request sequence begins when a user sends a prompt in the chat with \aitutor; each turn of the conversation issues one or more self-contained requests that carry the transcript-retrieval and course-recommendation tool calls described in Section~\ref{sec:aitutor-use-cases}; and no explicit termination step is required when the user closes the conversation, since no protocol-level session was opened in the first place.

Section~\ref{sec:implementation-limitations} discusses a consequence of this shift for the proof of
concept, which is implemented and evaluated against a legacy, session-based revision of MCP server (Chapter~\ref{chap:implementation}).

\subsubsection{MCP deployment pattern}
\UniMCP follows an \emph{API-gateway-centric} deployment pattern rather than a containerized,
per-tool microservice pattern, because Aalto already operates a central API management layer
(3scale) and a central identity provider (Azure AD); routing every MCP tool call through the existing AI Tutor router and the existing API management layer reuses this infrastructure instead of
duplicating governance logic at every tool. Within this pattern, the MCP server itself is deployed
remotely (on a shared RHEL server) rather than locally alongside each host process, so that a single
server instance can serve multiple concurrent user sessions over Streamable HTTP (ScR2) --- the
local, STDIO-based alternative would instead require one server process per session, which does not
scale to a shared, multi-user university deployment (Section~\ref{sec:ecosystem-challenges}). The
choice of deployment pattern is not fixed for every future \UniMCP integration: Section~\ref{sec:mcp-ecosystem} notes that the suitable pattern depends on the university's existing
architecture, operational resources, and risk tolerance, and a smaller-scale or higher-risk
integration might instead favor isolated, containerized MCP servers per tool at the cost of
duplicated governance logic.
